# Git、协作与 AI 使用规范

[返回开发规范总目录](DevelopmentGuidelines.md)

## 1. Git 基本工作流

1. 所有交付内容必须位于项目 Git 仓库的明确分支或 Worktree 中。
2. 不直接向 `main` 提交未经评审的功能修改。
3. 开始修改共享内容前先同步远端，并确认没有其他成员同时修改。
4. 一个分支聚焦一个任务；无法按期完成或依赖上游时应尽早同步。

推荐分支格式：

```text
feature/<module>-<summary>
fix/<module>-<summary>
content/<domain>-<summary>
docs/<summary>
```

## 2. 提交规范

### 2.1 提交粒度

1. 一次提交只处理一类相对完整的问题，最好不把多个无关修改混在同一次提交里。
2. 功能代码、资源迁移、格式化和文档调整原则上分别提交。
3. 提交前检查差异，移除无关文件和非必要格式变化。
4. 公共 Scene、Prefab、网络协议、Ghost 配置、`ProjectSettings` 和 `Packages` 修改应使用独立提交。

### 2.2 提交信息

提交信息必须写清楚“做了什么”，不使用“更新”“改了一下”“test”“修改代码”等无效描述。

提交前缀固定为：

| 前缀 | 用途 | 示例 |
|---|---|---|
| `chore:` | 杂项、整理、工具或经确认需要提交的生成内容变化 | `chore: 整理场景内节点命名` |
| `fix:` | Bug 修复 | `fix: 修复技能释放后冷却未刷新的问题` |
| `feat:` | 功能新增 | `feat: 完成玩家翻滚功能` |
| `update:` | 既有逻辑、数据、资源或格式的明确调整 | `update: 调整Blaster攻击间隔配置` |

可以增加可选模块范围：

```text
feat(player): 完成玩家翻滚功能
fix(combat): 修复技能释放后冷却未刷新的问题
update(ui): 调整结算面板布局
chore(scene): 整理场景节点命名
```

`update:` 只是类型前缀，冒号后的描述仍必须具体，禁止写成 `update: 更新代码`。

## 3. Unity 项目特殊要求

1. `.meta` 文件必须提交，不得遗漏。
2. 资产和 `.meta` 必须成对新增、移动和删除。
3. 禁止手工生成、复制或修改 GUID。
4. 修改公共 Scene、公共 Prefab、Animator Controller 前先同步，避免多人同时修改同一资源。
5. 不在未沟通的情况下移动公共资源位置，避免引用丢失和大范围冲突。
6. 场景和 Prefab 文件保持文本序列化，并使用 UnityYAMLMerge 处理冲突。
7. 不提交 `Library`、`Temp`、`Logs`、`obj`、用户设置、IDE 工程文件、代码转储和本地缓存。
8. Source Generator 输出、Dump 和分析文件只有被确认是正式产物时才能提交。

## 4. 提交前检查

每次提交前至少完成：

1. 项目能够正常运行，或已完成与修改范围相称的验证。
2. Console 中没有新增 Error。
3. Scene、Prefab 和 ScriptableObject 修改已正确保存。
4. 没有误提交无关文件。
5. 临时测试对象、测试代码、作弊入口和调试日志已清理。
6. 使用 `git status` 和 `git diff` 检查实际提交内容。
7. 资产与 `.meta` 已成对处理。
8. 没有 `<<<<<<<`、`=======`、`>>>>>>>` 等冲突标记。
9. 相关脚本能够重新编译。
10. 网络、Ghost、场景和构建配置修改已完成对应的双端或 Player 验证。

“没有新增 Error”不代表可以忽略已有 Error。若项目存在历史问题，提交说明必须区分历史问题和本次结果。

### 4.1 格式检查适用范围

1. 编码、行尾、行尾空格、缩进、注释率、注释语言和代码格式检查只约束团队手写维护的源码、脚本、配置和文档。
2. 以下非手写内容不参与文本格式清理，也不因格式工具产生的提示阻断提交：
   - Unity 自动生成或维护的文本序列化文件，例如 `.meta`、`.unity`、`.prefab`、`.asset`、`.mat`、Animator 和 Animation 数据
   - Source Generator、代码生成器、导入器或外部工具生成的代码与文本
   - 图片、模型、音频、字体、压缩包和其他二进制文件
   - 十六进制文件、转储、缓存、序列化数据和机器生成的中间表示
3. 不为通过格式检查而手工修改上述文件的空行、行尾空格、缩进、字段排列、编码或换行符，也不对其执行通用文本格式化器。
4. 非手写文件仍必须检查是否应当提交、是否与任务相关、是否损坏、是否包含冲突标记，以及是否满足大小、来源、许可证和 Git LFS 要求。
5. Unity 资产仍必须检查 `.meta` 配对、GUID 与引用完整性，并在 Unity 中验证 Scene、Prefab、ScriptableObject、材质和导入结果可正常加载。
6. `git diff --check`、格式化器和静态文本检查工具应限定到手写文件范围；非手写文件的格式告警记录后可忽略，但真实冲突、损坏和引用错误不得忽略。

## 5. 冲突处理

1. 不提交任何冲突标记。
2. 不理解的 Scene、Prefab、`ProjectSettings` 冲突不得擅自选择一方覆盖。
3. 场景和 Prefab 冲突解决后必须在 Unity 中打开，检查 Missing Script、引用和 Override。
4. 网络协议、Ghost 配置、Build Settings 和 Package 冲突必须由程序负责人参与确认。
5. 不使用“复制一个正式场景继续开发”作为长期冲突规避方案。

## 6. 大文件与 Git LFS

1. 大型 `.psd`、`.fbx`、`.wav`、`.exr` 和其他不可合并二进制资源应使用 Git LFS 或外部资产存储。
2. 不对文本格式的 `.unity`、`.prefab`、`.mat` 和 `.asset` 进行无差别 LFS 管理。
3. 引入大型文件前说明来源、用途、构建影响和许可证。
4. 清理已进入 Git 历史的大文件属于仓库级操作，必须由仓库负责人执行。

## 7. 所有权与协作

| 内容 | 默认负责人 | 额外要求 |
|---|---|---|
| `Art`、`Audio` | 美术/音频 | 运行时导入设置需程序或 TA 评审 |
| `Scenes` | 场景负责人 | 修改共享场景前声明范围 |
| `Prefabs` | 所属模块负责人 | Network Prefab 需程序评审 |
| `SO` | 策划及模块程序 | 字段结构变更需程序评审 |
| `Scripts` | 程序 | 公共接口变更说明影响范围 |
| `Shaders`、`Settings` | TA/程序 | 验证质量档位和目标平台 |
| `Packages`、`ProjectSettings` | 主程或授权程序 | 必须说明全项目影响 |

1. 不随意修改其他成员负责的模块；确需修改时先说明原因、影响范围和预期接口。
2. 目录越界不应一律阻断。自动脚本默认用于提示和要求 Review，对保护路径可设置严格门禁。
3. 上游依赖阻塞时立即联系负责人，明确交付内容和时间。
4. 修改公共逻辑、序列化字段、网络协议或配置结构时必须通知下游使用者。
5. 为策划和美术提供的字段、挂载点和工具应有清晰名称、默认值、Tooltip 或文档。
6. 沟通结论应写入任务、文档、Issue 或提交说明，不只保留口头约定。

## 8. AI 辅助开发

1. 可以使用 AI 辅助分析、编码、重构、测试、文档和资源制作。
2. 提交者对 AI 产出承担全部责任，AI 不能代替模块负责人 Review。
3. 使用前应提供本规范、Unity 版本、Packages 版本、目标 World、调用链和现有上下文。
4. AI 代码必须经过差异审查、API 版本核对、编译、测试和场景验证。
5. 禁止让 AI 手工生成或复用 `.meta` GUID。
6. AI 修改 Scene、Prefab、`ProjectSettings` 或 Ghost 配置时，必须人工逐项核对序列化差异。
7. 未经许可不得上传未公开源码、账号数据、密钥、付费资产或受限第三方内容。
8. AI 生成或处理的代码、美术、音频、字体和其他内容必须检查来源、许可证及可商用状态。
9. 删除模板式注释、调试输出、占位逻辑和未经理解的代码。
10. 大规模重构、批量重命名、协议修改和资源迁移必须先提交计划。
11. 评审重点是结果是否正确、符合项目上下文和当前 API，而不是使用哪一种 AI 工具。
