# AnimarsCatcher Navigation 模块架构重构方案

> 状态：R1-R5 已落地，R6 复审待执行
> 范围：`Assets/Scripts/Navigation` 当前 57 个 C# 文件
> 目标：在不改变现有导航行为、Burst/DOTS 数据布局和性能策略的前提下，降低认知复杂度，明确算法职责和依赖方向。

执行结果与验证证据见 [Navigation 重构执行报告（2026-08-20）](Reports/NavigationRefactor-Execution-20260820.md)。

---

## 1. 重构目标

当前 Navigation 模块已经具备完整的静态 Grid 烘焙、A*、HPA Corridor、Flow Field、动态 Overlay、Squad 阵型移动以及 Benchmark/Validation 能力。问题主要不是“缺少功能”，而是部分职责边界被压平：

- `NavigationGridPathAlgorithms` 同时承担 A*、坐标查询、端点投影、通行规则和成本模型；
- `NavigationGridFlowFieldAlgorithms` 同时承担 HPA Corridor、局部 Dijkstra、Integration Field、Flow Direction 和缓存；
- Flow Field 通过 `NavigationGridPathAlgorithms` 复用公共移动规则，形成假的“Flow Field 依赖 A*”关系；
- `AniSquad*` 已经是 Squad 级导航/阵型/移动系统，但仍混在 `Grid` 下；
- Benchmark 数据混入 `NavigationFlowFieldData`，工具代码与核心运行时职责边界不清；
- Scratch、Output、Cache 等成组数据以大量裸 `NativeArray` / `NativeList` 参数传播；
- 注释大量使用抽象、论文式措辞，增加而不是降低阅读成本。

本次重构的核心原则：

> **数据仍保持 Data-Oriented，API 和职责必须 Human-Oriented。**

运行时仍然使用 `struct`、`Blob`、`NativeArray`、`NativeList`、Generation、Indexed Heap 等现有技术，不为了“面向对象”引入 GC、托管对象图或多余间接层。

## 3. 各层职责

## 3.1 `Grid/Static` —— 静态导航世界

负责回答：

> 地图在导航意义上是什么？

包含：

- Cell 静态数据；
- Walkability；
- 八邻接 `NeighborMask`；
- Clearance；
- Region；
- Cluster；
- Portal；
- Portal Node；
- Abstract Edge；
- Scene Authoring；
- Editor Bake Asset 到 ECS Blob 的静态数据转换。

典型流水线：

```text
Scene Physics Sampling
        ↓
Cell Data
        ↓
Connectivity
        ↓
Clearance
        ↓
Region / Cluster
        ↓
Portal / Abstract Graph
        ↓
NavigationGridBlob
```

### `NavigationGridDirections`

八方向编号与 `NeighborMask` bit 位是静态数据协议的一部分，因此放在 `Static`，并成为整个模块唯一的方向编码实现。

禁止再次出现：

```text
NavigationGridAlgorithms.GetDirection
NavigationGridPathAlgorithms.GetDirection
NavigationGridPathAlgorithms.TryGetDirectionIndex
```

三套重复映射。

统一为类似：

```csharp
NavigationGridDirections.GetOffset(directionIndex, out dx, out dz);
NavigationGridDirections.TryGetIndex(dx, dz, out directionIndex);
```

### `NavigationEuclideanDistanceTransform`

将当前 `NavigationGridAlgorithms` 中的欧氏距离变换独立出来。

`NavigationGridBakingAlgorithms.CalculateClearance()` 只负责：

```text
构造 Clearance Source
→ 调用 EDT
→ 写回 Clearance
```

抛物线下包络等数学实现不再夹在普通 Grid 烘焙代码中。

## 3.2 `Grid/Overlay` —— 动态地图修正

负责回答：

> 静态 Grid 之上，此刻有哪些临时阻挡、额外成本和 Clearance 缩减？

包含：

- `NavigationDynamicOverlayCell`；
- `NavigationDynamicOverlayCluster`；
- Delta；
- Overlay Version；
- Cluster Version；
- Overlay 更新 System。

Overlay 不属于 A*、HPA 或 Flow Field。

它是上述所有运行时导航算法共同消费的动态地图层。

依赖：

```text
Overlay → Static
```

Overlay 不依赖 Pathfinding / Hierarchical / FlowField / Squad。

---

## 3.3 `Grid/Runtime` —— 公共运行时 Grid 规则

负责回答：

> 给定静态 Grid、动态 Overlay 和 Agent 参数，一次移动在运行时是否合法、代价是多少？

包含四类公共能力。

### Grid Query

```text
TryWorldToCell
GetCellWorldPosition
IsInside
TryProjectToNearestCell
```

### Traversal Rules

```text
CalculateRequiredClearance
CanAgentOccupy
CanAgentOccupyDynamic
CanAgentTraverseEdge
CanAgentTraverseEdgeDynamic
```

### Cost Model

```text
CalculateStepCost
GetDynamicExtraCost
```

统一成本语义：

```text
StepCost
= distance
× (terrain cost + clearance penalty)
+ dynamic extra cost
```

### 共享请求契约

`NavigationPathRequest`、`NavigationPathStatus` 和 `NavigationPathFailureReason` 属于 Runtime 契约，供 A*、HPA 和 Flow Field 共同消费。A* 专属的 `NavigationPathState` 和 `NavigationPathWaypoint` 仍归 `Pathfinding`。

### Dynamic Overlay View（可选但推荐）

用轻量 Burst-safe `readonly struct` 包住动态 Overlay NativeArray 查询：

```csharp
readonly struct NavigationDynamicOverlayView
{
    bool IsBlocked(int cellIndex);
    float GetExtraCost(int cellIndex);
    float GetClearanceReduction(int cellIndex);
}
```

目的不是 OOP 封装，而是消除全模块重复的：

```csharp
dynamicOverlay.IsCreated &&
cellIndex >= 0 &&
cellIndex < dynamicOverlay.Length
```

### 关键规则

`Runtime` 不实现 A*、Dijkstra、HPA 或 Flow Field。

它只定义这些算法共同遵守的 Grid 物理/成本规则。

## 3.4 `Grid/Pathfinding` —— 单体完整路径

负责回答：

> 从 A 到 B，返回一条明确的 Cell/Waypoint 路径。

流水线：

```text
NavigationPathRequest
        ↓
Endpoint Projection
        ↓
A*
        ↓
Raw Parent Chain
        ↓
Cost-aware Path Smoothing
        ↓
NavigationPathResult
```

### `NavigationGridPathfinder`

只保留 A* 编排与搜索。

不再拥有：

- 通用方向编码；
- Occupancy；
- Edge Traversal；
- Step Cost；
- Dynamic Overlay 基础查询；
- 通用世界坐标转换。

### `NavigationAStarOpenSet`

保留 A* 特有的 F = G + H 排序、Octile Heuristic、稳定 tie-break。

不要与 Flow Field/Dijkstra 使用的 `IndexedFloatHeap` 强行统一成一个超级泛型搜索框架。

### `NavigationPathSmoothing`

负责：

```text
Reconstruct Parent Chain
→ Line Traversal Check
→ Cost-aware greedy smoothing
```

A* 搜索和路径平滑不再写在同一个大函数中。

### Scratch

将当前裸参数：

```text
gCosts
parents
heap
heapPositions
nodeGenerations
```

组合为语义结构：

```csharp
NavigationAStarScratch
```

仍然由 Job/System 持有 Native 容器生命周期，Solver 只接收引用。

## 3.5 `Grid/Hierarchical` —— HPA Corridor

负责回答：

> 从起点 Cluster 到终点 Cluster，宏观上应该经过哪些 Cluster / Portal？

流水线：

```text
Prepared Start / End
        ↓
Start Cluster Local Costs
        ↓
End Cluster Reverse Local Costs
        ↓
Abstract Portal Graph Search
        ↓
Parent Reconstruction
        ↓
NavigationCorridor
```

从当前 `NavigationGridFlowFieldAlgorithms` 抽离：

- `TryBuildAbstractCorridor`；
- `RunLocalCosts` 中与 Corridor 相关部分；
- Abstract Node Dijkstra；
- Corridor Cluster / Portal 重建；
- Hierarchical Waypoint 生成相关逻辑。

### `NavigationCorridorData`

从当前 `NavigationFlowFieldData.cs` 移出：

```text
NavigationCorridorCluster
NavigationCorridorPortal
NavigationHierarchicalWaypoint
```

这些是 HPA 结果，不是 Flow Field 本身。

## 3.6 `Grid/FlowField` —— Corridor 内局部导航场

负责回答：

> 已经确定宏观 Corridor 后，Corridor 内每个 Cell 应该往哪里走？

流水线：

```text
NavigationCorridor
        ↓
Reverse Dijkstra
        ↓
Integration Cost
        ↓
Flow Direction
        ↓
NavigationFlowField
```

### `NavigationIntegrationFieldSolver`

负责：

- 标记允许搜索的 Corridor Cluster；
- 从 Target 反向 Dijkstra；
- 生成 Integration Cost；
- 从下降邻居生成 Flow Direction；
- 输出稀疏 `NavigationFlowFieldCell`。

它不再负责寻找 Corridor。

### `NavigationFlowFieldCache`

从当前大算法类中独立：

```text
Cache Key
Corridor Hash
Overlay Signature
Lookup
Append
Insert
```

System 仍持有缓存 NativeList 生命周期；Cache 类型只是组织缓存操作和参数。

### Workspace / Output

当前 Flow Field Build 的大量参数应组合为：

```text
NavigationCellSearchScratch
NavigationAbstractSearchScratch
NavigationFlowFieldWorkspace
NavigationFlowFieldOutput
NavigationFlowFieldCacheWorkspace
```

目的：把“这几个数组属于同一算法状态”编码进类型，而不是要求读者通过 20 个函数参数自行推理。

## 3.7 `Squad` —— Squad 级导航与阵型移动

Squad 与 `Grid` 平级。

它负责回答：

> 一个 Squad 如何利用 Grid/Flow Field 移动，并维持阵型和成员行为？

包含：

```text
Command / Lifecycle
        ↓
Target Resolve
        ↓
Flow Field Request
        ↓
Anchor Movement
        ↓
Adaptive Formation
        ↓
Slot Layout
        ↓
Hungarian Assignment
        ↓
Member Preferred Velocity
        ↓
Movement Commit
        ↓
Progress / Arrival
```

Squad 是 Grid Navigation 的消费者，不是 Grid 本身。

### 拆分 `AniSquadMovementAlgorithms`

当前类同时包含两类完全不同的算法。

#### `AniSquadFormationAlgorithms`

```text
CalculateColumnCount
CalculateAdaptiveColumnCount
CalculateSlotRole
CalculateSlotOffset
CalculateMeanRowOffset
TrySolveMinimumCostAssignment (Hungarian)
```

#### `AniSquadSteeringAlgorithms`

```text
TryGetFlowDirection
CalculateSlotVelocity
CalculateAnchorVelocity
CalculateSlotWorldPosition
```

不再用一个“MovementAlgorithms”同时包含 Hungarian 和速度计算。

## 4. 最终依赖方向

依赖必须保持单向：

```text
                    ┌──────────────┐
                    │ Grid/Static  │
                    └──────┬───────┘
                           │
                  ┌────────┴────────┐
                  ▼                 ▼
            Grid/Overlay       Grid/Runtime
                  │                 ▲
                  └────────┬────────┘
                           │
               ┌───────────┼────────────┐
               ▼           ▼            ▼
          Pathfinding  Hierarchical   (other grid consumers)
                           │
                           ▼
                       FlowField
                           │
                           ▼
                         Squad

Tooling → 可以消费上述任意层
```

更精确地写：

```text
Static

Overlay       → Static
Runtime       → Static + Overlay
Pathfinding   → Runtime
Hierarchical  → Runtime
FlowField     → Runtime + Hierarchical
Squad         → Runtime + FlowField + Hierarchical data as needed
Tooling       → all (read/test/benchmark/editor only)
```

### 禁止依赖

必须消除以下关系：

```text
FlowField → Pathfinding
Hierarchical → Pathfinding
Static → Runtime
Static → Overlay
Grid → Squad
Core Runtime → Squad
Core Runtime → Benchmark
```

特别是以后不得再出现：

```csharp
NavigationGridFlowFieldAlgorithms
    → NavigationGridPathAlgorithms.CalculateStepCost(...)
```

正确关系应为：

```text
FlowField          ──┐
Hierarchical       ──┼→ NavigationGridTraversal / NavigationGridCost
Pathfinding        ──┘
```

## 5. Job / System 的定位

`Job` 和 `System` 不是独立算法层。

统一理解：

```text
Algorithm / Solver
        ↑ called by
Job
        ↑ scheduled by
System
```

### Solver

负责：

- 算法本身；
- Burst-safe；
- 不访问 World；
- 不管理 ECS 生命周期。

### Job

负责：

- Batch；
- NativeContainer 参数；
- Scratch reuse；
- Burst 调度边界。

### System

负责：

- Pending / Searching / Succeeded / Failed 生命周期；
- 收集请求；
- Schedule / Complete；
- Version 过期检查；
- ECS Buffer 写回；
- Native 容器生命周期；
- JobActivity 与 Overlay 同步。

因此 Job/System 跟随所属 feature 放置，不建立全局 `Jobs/` 和 `Systems/` 目录。

## 7. 关键类型重构

### 7.1 `NavigationGridPathAlgorithms` 最终消失

当前职责拆分为：

```text
NavigationGridPathfinder
    A* search

NavigationAStarOpenSet
    F/G/H ordering

NavigationPathSmoothing
    reconstruction + smoothing

NavigationGridQuery
    world/cell conversion + endpoint projection

NavigationGridTraversal
    occupy + traverse

NavigationGridCost
    step cost

NavigationGridDirections
    direction encoding
```

Flow Field 和 HPA 不再依赖任何叫 `PathAlgorithms` 的公共工具类。

### 7.2 `NavigationGridFlowFieldAlgorithms` 最终消失

当前职责拆分为：

```text
NavigationGridCorridorSolver
    HPA corridor

NavigationIntegrationFieldSolver
    reverse Dijkstra + flow direction

NavigationFlowFieldCache
    cache lookup/insertion/signatures
```

FlowField Job 负责串联：

```text
Prepare Request
→ Corridor Solver
→ Cache Lookup
→ Integration Solver (miss only)
→ Output Result
```

Job 可以负责 orchestration，但算法实现不得重新合并成一个 1000+ 行 static class。

## 9. 注释规范

注释目标：降低理解成本，而不是证明代码“很严谨”。

### 保留

解释：

- 为什么需要这个约束；
- 容易违反直觉的算法行为；
- 数据协议；
- 边界条件；
- correctness 依赖；
- 非显然性能设计。

例如：

```csharp
// Grid 外也视为障碍，否则边缘 Cell 会高估 Clearance。
```

```csharp
// 两条路径一样贵时固定选较小 CellIndex，保证结果稳定。
```

```csharp
// 对角移动要求两个侧边 Cell 都能容纳 Agent，避免大体型从角上挤过。
```

### 删除/改写

避免：

```text
权威表示
结果发布
Generation 隔离槽位归属
严格改善判断
宏观序列
可观测字段
原子写回
协议语义
```

除非这些词在上下文中确实具有具体技术含义。

### 基本原则

> 函数名说明“做什么”；代码说明“怎么做”；注释重点解释“为什么必须这么做”。

## 10. 重构阶段

架构重构和算法修改严格分离。

### R0 — Baseline 冻结

目标：建立行为基线，不改算法。

- 当前代码必须编译；
- Stage 1–5 validation 保存结果；
- Path / Flow Field / Movement benchmark 保存基线；
- 记录关键 fixture 输出；
- 不修改算法语义。

### R1 — Shared Runtime Rules

低风险、收益最大。

1. 建立 `NavigationGridDirections`，删除重复方向映射；
2. 建立 `NavigationGridTraversal`；
3. 建立 `NavigationGridCost`；
4. 建立 `NavigationGridQuery`；
5. A*、HPA、Flow Field、Squad 改为共同调用 Runtime Rules；
6. 行为和 benchmark 必须保持一致。

完成标志：

```text
FlowField 不再引用 NavigationGridPathAlgorithms
Squad 公共 Grid 查询不再引用 NavigationGridPathAlgorithms
```

### R2 — A* Vertical Slice

1. `NavigationGridPathfinder`；
2. `NavigationAStarOpenSet`；
3. `NavigationPathSmoothing`；
4. `NavigationAStarScratch`；
5. Job/System 移入 Pathfinding；
6. 删除 `partial NavigationGridPathAlgorithms`。

不改变：

- heuristic；
- tie-breaking；
- generation；
- smoothing tolerance；
- output format。

### R3 — HPA / Flow Field 分离

1. 从 `NavigationGridFlowFieldAlgorithms` 抽出 `NavigationGridCorridorSolver`；
2. 抽出 `NavigationIntegrationFieldSolver`；
3. 抽出 `NavigationFlowFieldCache`；
4. 建立 Workspace / Output grouping；
5. Flow Field Job 只负责编排；
6. 删除原 1000+ 行大类。

不在本阶段修算法问题。

### R4 — Squad 独立

1. `AniSquad*` 从 `Grid` 移到 `Navigation/Squad`；
2. 拆 Formation / Steering Algorithms；
3. Squad 只通过公开 Grid Runtime / FlowField API 消费 Grid；
4. Grid 代码禁止依赖 Squad。

### R5 — Static / Tooling 整理

1. EDT 从 Grid baking class 抽离；
2. Static 文件归位；
3. Benchmark Data 从 FlowField Data 移出；
4. Editor / Validation / Benchmark 归位；
5. 清理 AI 风格注释；
6. 最后再进行物理文件移动，避免早期产生巨大无意义 diff。

### R6 — Algorithm / Performance Review

只有结构重构全部通过原有验收后，才处理算法问题。

当前已知需要单独评估的事项包括：

- 动态 Overlay 使静态 HPA Corridor 失效时，目前可能直接 `NoPath`，是否需要重新选择 Corridor；
- 动态 `ExtraCost` 对宏观 Corridor 选择的影响；
- Flow Direction 平滑向量抵消到零时的 fallback；
- Flow Direction 的平滑离散选择是否允许牺牲 Bellman 最优 successor；
- Hierarchy Builder 中 shortest-cost path 与 widest-clearance path 分别求解后写入同一抽象边的语义一致性；
- Path smoothing 的最坏复杂度；
- Flow Field cache 命中后的 Field copy / start-cost 线性查询；
- Cache eviction 策略。

这些问题不得混入 R1–R5 的结构重构 diff。

## 11. Namespace 策略

第一轮结构重构**不强制同步修改 namespace**。

建议先保持：

```csharp
AnimarsCatcher.Navigation.Grid
```

以及现有 Squad 相关引用能够正常编译。

原因：

- 文件夹移动和 namespace 变化同时发生会制造大量 `using` 噪音；
- 不利于 code review；
- 不利于 bisect；
- 结构重构本身已经足够大。

当 R1–R5 稳定后，再单独决定是否使用：

```text
AnimarsCatcher.Navigation.Grid.Static
AnimarsCatcher.Navigation.Grid.Pathfinding
AnimarsCatcher.Navigation.Grid.FlowField
AnimarsCatcher.Navigation.Squad
```

Namespace migration 应单独 commit。

## 14. 最终原则

本模块以后遵循以下规则：

1. **按职责划分 feature，不按 Unity 类型划分目录。**
2. **Static 描述世界，Runtime 描述移动规则，Solver 负责搜索。**
3. **A*、HPA、Flow Field 是兄弟算法，不互相充当工具类。**
4. **HPA 负责 Corridor，Flow Field 负责 Corridor 内的局部场。**
5. **Squad 消费 Navigation，不属于 Grid。**
6. **Overlay 是横切动态地图层，不属于任何单一 Pathfinder。**
7. **Scratch/Cache/Output 可以 DOD，但必须用语义结构组织 API。**
8. **注释解释原因，不把普通代码翻译成论文。**
9. **结构重构与算法优化分 commit、分阶段完成。**
10. **任何新增功能先决定属于哪一层，再决定放在哪个文件。**
